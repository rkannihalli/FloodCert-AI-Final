## FEATURE 1 — User Access Request Form

### 1a — Access Request Page
When a new user visits the website and does not have an account, show an "Request Access" page (before any flood cert functionality is accessible) that collects the following fields — all mandatory:

- First Name
- Last Name
- Company Name
- Company Address (Street, City, State, ZIP)
- Email Address
- Contact Number

**Validation rules:**
- Email must be valid format
- Contact number must be 10 digits (US format), display as (XXX) XXX-XXXX
- All fields required — do not allow submission with any blank field
- On submission, save the request to the database with status = "Pending"
- Send an automated confirmation email to the user: "Your access request has been received. You will be notified once approved."
- Send a notification email to the Admin that a new access request has been submitted, including all submitted details.

### 1b — Access Approval Workflow
- Admin must approve or reject each access request from the Admin Dashboard.
- On approval: create a user account, assign them to their company (create company if new, or link to existing company if company name matches), and send the user a welcome email with login credentials or a set-password link.
- On rejection: send the user an email notifying them their request was not approved.
- Status values: Pending | Approved | Rejected
- Admin can change status at any time.

## FEATURE 2 — Company-Based Access Control & Multi-Tenancy

### 2a — Data Isolation by Company
- Every flood certificate run, report, and history record must be tagged with the company_id of the user who ran it.
- When any logged-in user views history or reports, they can ONLY see records belonging to their own company_id.
- Enforce this at the database query level — never rely only on UI-level filtering. Every query for history/reports must include a WHERE company_id = current_user.company_id clause.
- No user (except Admin) can access, view, or search records from another company under any circumstance.

### 2b — Company User Management
- Multiple users from the same company (matched by Company Name at registration) are grouped under the same company account.
- Users within the same company can see all flood cert history generated by anyone in their company, but cannot see other companies' data.

## FEATURE 3 — Admin Dashboard

### 3a — Company-Wise Access View
Admin has a dedicated dashboard section: "Access Requests" showing:
- All submitted access requests with: Name, Company, Email, Contact, Address, Date Submitted, Status (Pending/Approved/Rejected)
- Filter by: Company Name, Status, Date Range
- Approve / Reject buttons per request
- Bulk approve/reject option

### 3b — Company-Wise History View
Admin can view flood certificate history organized by company:
- Dropdown or sidebar: select any company → see all flood cert runs by that company and all users under it
- Columns: Date/Time, User Name, Property Address, Report Result, Flood Zone, Panel Number, Community Number, Status
- Admin can also view history for individual users within a company
- Admin can search/filter history by: company, user, date range, property address, flood zone

### 3c — Admin Delete History
- Admin can delete any individual history record or bulk-delete records (by company, by date range, or selected records).
- History records are NEVER automatically deleted — they persist indefinitely until an Admin explicitly deletes them.
- Non-admin users have NO delete capability — remove any delete button/option from the user-facing UI.
- Before deletion, show a confirmation dialog: "Are you sure you want to permanently delete [N] record(s)? This cannot be undone."
- Log all admin deletions in a separate audit log table: (admin_user_id, deleted_record_ids, timestamp, reason_optional) — this audit log itself is never deletable from the UI.

### 3d — Admin Access to All Companies
- Admin can switch between any company view without logging out.
- Admin's own flood cert runs are tagged under an "Admin" internal company and do not appear in any regular company's history.

## FEATURE 4 — Life-of-Loan (LOL) Monitoring — Full Implementation

### 4a — What to Track
When a flood certificate is generated with Life-of-Loan Monitoring = ON, store the following baseline values in the lol_monitoring table:

- loan_id (or property + lender reference)
- property_address (full)
- lender_email (required — capture at time of cert generation)
- lender_name
- baseline_panel_number (NFIP Community Panel Number at time of cert)
- baseline_effective_date (FIRM Panel Effective/Revised Date at time of cert)
- baseline_flood_zone (Flood Zone at time of cert, e.g., AE, X, X500)
- baseline_community_number (NFIP Community Number)
- created_at
- last_checked_at
- status: Active | Closed

### 4b — Change Detection Logic
Run a scheduled background job (daily, or configurable interval) that:
1. For each active LOL monitoring record, re-query the FEMA NFIP FIRM spatial layer using the stored property coordinates.
2. Compare current FIRM data against stored baseline for ALL of:
   - Panel Number (Community Panel Number)
   - FIRM Panel Effective/Revised Date
   - Flood Zone designation (including X vs X500 distinction)
   - NFIP Community Number
3. If ANY of these four values have changed, trigger an alert immediately.

### 4c — Lender Email Alert
On detection of a change, send an automated email directly to the lender_email on file. Email must include:

Subject: "FLOOD ZONE CHANGE ALERT — Action Required: [Property Address]"

Body must include:
- Property Address
- Loan Reference / Certificate ID
- A table showing: Field | Previous Value | Current Value for each changed item
- Date/time of detected change
- Clear call-to-action: "A change has been detected in the FIRM data for this property. Please re-run the flood certificate immediately to ensure compliance."
- Contact/support information

### 4d — Alert Logging
- Every alert sent must be logged in a lol_alerts table: (monitoring_id, changed_fields, old_values, new_values, alert_sent_at, lender_email, email_status: Sent|Failed)
- If the email fails to send, retry up to 3 times, then mark as Failed and flag for Admin review.
- Admin dashboard must have a "LOL Alerts" section showing all alerts sent, with filter by company, date, and property.

### 4e — LOL Monitoring Management
- Users can view all active LOL monitoring records for their company.
- Users can mark a monitoring record as "Closed" (e.g., loan paid off) — this stops future checks but preserves the history.
- Admin can view and manage all LOL monitoring records across all companies.

## DATABASE SCHEMA ADDITIONS

Add the following tables (or equivalent in your DB):

```sql
-- Access requests
CREATE TABLE access_requests (
  id UUID PRIMARY KEY,
  first_name VARCHAR,
  last_name VARCHAR,
  company_name VARCHAR,
  company_address TEXT,
  email VARCHAR UNIQUE,
  contact_number VARCHAR,
  status VARCHAR DEFAULT 'Pending', -- Pending | Approved | Rejected
  submitted_at TIMESTAMP DEFAULT NOW(),
  reviewed_at TIMESTAMP,
  reviewed_by UUID -- admin user id
);

-- Companies
CREATE TABLE companies (
  id UUID PRIMARY KEY,
  name VARCHAR UNIQUE,
  address TEXT,
  created_at TIMESTAMP DEFAULT NOW()
);

-- Users
CREATE TABLE users (
  id UUID PRIMARY KEY,
  first_name VARCHAR,
  last_name VARCHAR,
  email VARCHAR UNIQUE,
  contact_number VARCHAR,
  company_id UUID REFERENCES companies(id),
  role VARCHAR DEFAULT 'user', -- user | admin
  created_at TIMESTAMP DEFAULT NOW()
);

-- Flood cert history (add company_id if not already present)
ALTER TABLE flood_cert_history ADD COLUMN IF NOT EXISTS company_id UUID REFERENCES companies(id);
ALTER TABLE flood_cert_history ADD COLUMN IF NOT EXISTS user_id UUID REFERENCES users(id);

-- Admin audit log for deletions
CREATE TABLE admin_deletion_log (
  id UUID PRIMARY KEY,
  admin_user_id UUID REFERENCES users(id),
  deleted_record_ids TEXT[], -- array of deleted history IDs
  deleted_at TIMESTAMP DEFAULT NOW(),
  reason TEXT
);

-- LOL Monitoring
CREATE TABLE lol_monitoring (
  id UUID PRIMARY KEY,
  company_id UUID REFERENCES companies(id),
  user_id UUID REFERENCES users(id),
  property_address TEXT,
  lat DECIMAL,
  lon DECIMAL,
  lender_name VARCHAR,
  lender_email VARCHAR,
  baseline_panel_number VARCHAR,
  baseline_effective_date DATE,
  baseline_flood_zone VARCHAR,
  baseline_community_number VARCHAR,
  status VARCHAR DEFAULT 'Active', -- Active | Closed
  created_at TIMESTAMP DEFAULT NOW(),
  last_checked_at TIMESTAMP
);

-- LOL Alert Log
CREATE TABLE lol_alerts (
  id UUID PRIMARY KEY,
  monitoring_id UUID REFERENCES lol_monitoring(id),
  changed_fields TEXT[],
  old_values JSONB,
  new_values JSONB,
  alert_sent_at TIMESTAMP DEFAULT NOW(),
  lender_email VARCHAR,
  email_status VARCHAR DEFAULT 'Sent' -- Sent | Failed
);
```
